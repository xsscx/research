# Incident: Review-Driven Root CMake Repair Loop on iccDEV PR #2480

Date: 2026-09-08

## Summary

InternationalColorConsortium/iccDEV#2480 added a repository-root CMake entry
point that forwards to the canonical `Build/Cmake` graph. The branch received
serial repair pushes after Cloud Agent reviews identified defects in packaging,
manifest parity, root-forwarded multi-config runtime staging, canonical runtime
fallback behavior, CI path selection, archive layout, static-library script
probes, and build-system documentation.

The technical defects were repaired, but the process failed. Each review
finding was initially handled as a narrow edit rather than as proof that the
complete root-forwarding contract had not been audited. That caused later
reviews to find unchanged or equivalent surfaces that should have been
included in the same local repair.

## Impact

- Four Cloud Agent reviews identified actionable findings after publication:
  `5148148631`, `5148356587`, `5148667406`, and `5148750193`.
- Five repair commits were pushed after the original root-entry-point commit:
  `1dfc69b5`, `788582aa`, `9b36754e`, `02538010`, and `3a4700b9`.
- CI and Cloud Agent review became a discovery path for root/canonical build
  topology, packaging, CI gating, shell-script behavior, and documentation
  requirements.
- Maintainer review time and hosted runner capacity were used to identify
  counterpart paths that a cumulative local audit should have found.

## What Went Wrong

1. The root CMake entry point was not treated as a single multi-surface
   contract. The audit needed to cover the root forwarding graph, canonical
   graph, outer and inner binary trees, direct and preset configuration,
   package targets, test-runtime manifests, CI path filters, dependency
   manifests, regression helpers, and documentation claims together.
2. Review comments were treated as a list of line-local fixes. A finding in
   one path did not consistently trigger a search for equivalent uses. The
   second CAM static-library cache probe was one example; root and canonical
   cache paths were another.
3. Focused local commands proved individual repairs but were not consistently
   connected to an exact-head cumulative contract matrix before publication.
   A passing root-forwarded multi-config fixture did not prove the direct
   canonical layout until CI exercised it.
4. CI selection and packaging output were not treated as consumers of the same
   public CMake-entry-point change. The changed manifests needed to select the
   example-consumer path, and archive contents needed a direct assertion
   independent of a successful packaging target.
5. Build-system documentation was not reconciled against both implementation
   and preset metadata. Direct configuration accepts CMake 3.18+, while the
   checked-in preset catalogs require CMake 3.23+; an unqualified single
   minimum was inaccurate.
6. The review-cycle stop rule was not an effective action gate. Continued
   repair pushes occurred only after explicit maintainer direction, but the
   required branch-only cumulative audit should have preceded each coherent
   repair rather than following individual review comments.

## Root Cause

The governing documents already required a complete `origin/master..HEAD`
review, an exact-head evidence record, active and suppressed review inventory,
and a producer-consumer contract matrix before follow-up publication. The
failure was execution: the local scope model was rebuilt incrementally instead
of being invalidated and reconstructed after each review exposed an omission.

Urgency to resolve and push did not change the required order of work. The
correct interpretation was to assemble one complete repair for all confirmed
counterparts, validate the full mapped contract, and then publish it. Treating
each incoming finding as the next immediate change recreated the
review-as-discovery loop documented by prior incidents.

## Required Remediation

1. For a root build-system change, create an explicit entry-point matrix before
   editing or repairing: root and canonical source directories; root and
   canonical binary directories; single and multi-config generators; direct
   configuration and presets; package targets; runtime staging; CI consumers;
   manifests; scripts; and documentation.
2. After a review finding, search every equivalent producer and consumer before
   making a repair. The named file is evidence of a class of contract, not a
   complete repair scope.
3. Bind the local review, matrix, and validation evidence to the exact proposed
   push SHA. Any new file or behavior change invalidates earlier readiness
   evidence until the changed surface is incorporated.
4. Test both positive and negative topology cases: root forwarding and direct
   canonical configuration; outer and inner cache locations; normal and
   multi-config runtime staging; package-target success and archive contents;
   CI selection and non-selection behavior.
5. Inventory all review threads and review summaries, including suppressed
   findings, before planning a repair. Do not use resolved-thread count or a
   focused passing test as readiness evidence.
6. Treat a second automated-review blocker as a stop signal. Do not use
   serial review findings to drive individual pushes; return to branch-only
   grooming and report the missing cumulative gate before further publication.

## Decision

The PR #2480 technical repairs do not erase the process failure. This incident
is another instance of the pattern recorded in the governance history:
incomplete local contract mapping, line-local review repair, and repeated
publication before an exact-head cumulative readiness decision. Future root
build-system work must prove the entire forwarding contract locally before a
repair push, not use CI or Cloud Agent review to find the next counterpart.
