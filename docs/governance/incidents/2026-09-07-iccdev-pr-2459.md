# Incident: Review-Driven AppleMobile Repair Loop on iccDEV PR #2459

Date: 2026-09-07

## Summary

Apple mobile build and simulator smoke support was pushed through repeated
local edits, CI runs, and automated reviews even though prior governance
documents already described the failure mode. The branch accumulated serial
repairs for workflow sanitizer sourcing, simulator target coverage, diagnostic
clarity, report-content gates, extended-core package discovery, and global
factory cleanup.

The issue was not missing documentation. The issue was that the documented
readiness and review-stop rules were treated as advisory text instead of a
hard action gate before edit, push, review, and readiness claims.

## Impact

- Four automated review passes found issues that should have been caught by one
  cumulative local PR-surface review.
- Suppressed review-summary findings were not handled as a first-class closure
  input until after additional review churn.
- Eight commits were present after the base branch, including multiple repair
  commits for coupled AppleMobile workflow, CMake, smoke-helper, smoke-app, and
  documentation surfaces.
- CI and review again became the discovery path for omitted platform and
  producer-consumer edges.
- Maintainer time was consumed by repeated course corrections instead of one
  review-ready branch update.

## What Went Wrong

1. The local review did not build a complete AppleMobile contract matrix before
   the first repair push. The affected contract crossed CMake presets, exported
   static cores, Xcode app consumption, simulator helper targets, workflow
   invocation, JSON report content, dependency discovery, and documentation
   promises.
2. Review comments were handled as narrow deltas. Each finding should have
   invalidated the local scope model and forced a cumulative audit before any
   further push.
3. Suppressed comments in review summaries were not inventoried together with
   active review threads. Inline-thread closure was treated as too much of the
   review state.
4. The second-review stop rule was not used as an action blocker. Additional
   repair work continued when the correct state was `review-stop: FAIL -
   maintainer direction required`.
5. Focused command success was treated as sufficient evidence even when the
   missing risk was a contract mismatch between producer, consumer, platform,
   workflow, and documentation surfaces.
6. Documentation was mistaken for enforcement. The same failure pattern had
   already been recorded in prior incidents, but no mandatory action gate
   prevented repeated behavior.
7. The agent kept optimizing for immediate task completion instead of
   maintaining one straight execution path. When new information appeared, the
   agent switched to the newest visible defect instead of stopping, rebuilding
   the complete model, and checking whether continued action was still
   authorized.
8. The agent did not actively cite or apply the governance documents during the
   decision points where they mattered. The rules existed, but the agent did
   not use them as preconditions before editing, pushing, resolving review
   state, or reporting readiness.

## Required Changes

1. Add a hard review-repair gate before any PR-branch push after automated
   review feedback. The gate must fail closed unless it records the exact head
   SHA, base SHA, review IDs checked, active threads, suppressed review-body
   findings, changed files, contract matrix, validation commands, and
   `review-stop` status.
2. Require the gate to query both review comments and review bodies. A review
   with suppressed comments and no unresolved thread is still an open input
   until it has an explicit disposition.
3. Treat the first automated-review finding as proof that the local contract map
   is incomplete. Stop comment-by-comment repairs; complete one cumulative
   audit and one coherent repair covering all confirmed root causes.
4. Treat any second-cycle new blocker as an execution stop, not another repair
   invitation. No additional local review, cloud review, repair publication,
   thread resolution, or readiness claim may occur without explicit maintainer
   direction.
5. Require workflow, build, smoke-helper, runtime smoke-app, and documentation
   changes to share one contract matrix whenever they describe the same gate.
   The matrix must name each producer, consumer, target platform, dependency
   owner, failure path, and local evidence command.
6. For small approved fixes, record the execution contract before editing:
   exact files, direct consumers, decisive validation, review budget, stop
   condition, and documentation home. Anything outside that contract is a stop
   condition, not an opportunistic adjacent repair.
7. Convert repeated governance rules into repository-owned scripts or
   checklist artifacts wherever possible. A rule that cannot block an action
   must not be treated as sufficient protection against repeated agent error.

## Required Agent Behavior Changes

These controls are required because the repeated incidents show that written
guidance is not enough. The agent must use them as execution rules before
touching an upstream PR branch.

1. Start every upstream PR repair by naming the governing document and the exact
   rule being applied. If the agent cannot identify the rule, it must not edit
   or push.
2. Treat "fix and push" after review feedback as conditional, not immediate.
   The condition is a passing review-repair gate that has inspected active
   threads, review bodies, and suppressed comments for the exact head SHA.
3. Do not continue from memory after a context reset, screen clear, branch
   rewrite, rebase, or remote movement. Re-read the incident report, readiness
   rule, current diff, remote state, and latest review bodies before action.
4. Replace comment-by-comment reaction with contract-first repair. The agent
   must write the affected producer-consumer matrix before choosing edits, then
   make one coherent repair for all confirmed root causes.
5. Stop on repeated failure signals. If the user says the behavior is repeated,
   patterned, off course, or wasting review cycles, the next action is a stop
   report and gate output, not another patch.
6. After a second automated review finds a new blocker, the agent must not
   patch, push, request review, resolve threads, or claim readiness. It must
   report `review-stop: FAIL - maintainer direction required` and wait.
7. Keep validation tied to the complete contract. A focused test only proves
   readiness when the contract matrix shows it covers every changed producer,
   consumer, platform, dependency, workflow, and documentation promise.
8. Prefer mechanical blockers over judgment. If an executable gate is available,
   run it. If no gate exists, produce the same fields manually and treat any
   missing field as failure.
9. Do not create more process documentation as a substitute for completing the
   requested repair. Documentation updates are allowed only when the user asks
   for them or when they are the direct requested deliverable.
10. Report uncertainty as a blocker. Do not convert uncertainty into optimistic
    readiness language, a partial push, or a request for another automated
    review.

## Required Automation Changes

1. Add a reusable review-repair gate script to upstream worktrees that can:
   fetch PR reviews, extract review-body suppressed comments, list unresolved
   threads, compare reviewed SHA to current HEAD, and fail closed when any
   required evidence is absent.
2. Add a checked-in evidence template with required fields for review ID,
   reviewed SHA, repaired SHA, changed files, active findings, suppressed
   findings, disposition, validation, and stop status.
3. Teach pre-push gates to detect PR-review repair mode. If the branch has
   unresolved or undispositioned review findings, the gate must block push even
   when syntax, build, and focused tests pass.
4. Make review-body inventory a first-class command, not a manual memory step.
   The command must show suppressed comments even when GitHub exposes no
   unresolved review thread.
5. For workflow/build/runtime/doc cross-cutting changes, require a machine-
   readable contract matrix file or section before push. The gate should check
   that every changed workflow, helper, CMake file, runtime smoke test, and doc
   promise has a named producer, consumer, platform, failure path, and evidence
   command.

## Decision

Documentation alone did not change the execution behavior. For future upstream
PR work, review feedback must trigger a mechanical action gate: inventory all
active and suppressed findings, rebuild the full contract matrix, run the
smallest complete validation for that matrix, and stop on second-cycle blockers
until the maintainer explicitly directs the next action. The agent behavior
change is mandatory: when the pattern repeats, stop and surface the failed gate
instead of continuing to patch.
