# Incident: Repeated Review-Stop Failure on iccDEV PR #2471

Date: 2026-09-07

## Summary

`InternationalColorConsortium/iccDEV` PR #2471 added the
`examples/ios-clut-editor` iOS/iPadOS and Mac Catalyst proof-of-concept app.
The work was intended to avoid the prior #2468 failure mode by doing local
grooming, local review, physical-device QA, and whole-PR surface review before
using hosted review as a final confirmation gate.

That standard was not met. The first local review before PR publication found
one iPad picker defect, but it did not prove the full command-contract matrix
or the live-render state machine. After publication, three API-visible Copilot
PR reviews each reported only partial file coverage and continued to find
actionable issues, including `Previously missed` findings in review summaries.
The user reported the lived review experience as a sixth Cloud Agent review;
even the API-visible count of three posted reviews was already beyond the
review-stop threshold because the second and third reviews found new blockers.

The primary failure was not one missed race or one shell parser bug. The
primary failure was that the branch was allowed to use cloud review as a serial
discovery loop after local readiness had been claimed.

## Impact

- The PR accumulated at least five commits after `origin/master`:
  `d0e537fc`, `48d7723a`, `180f93e`, `ed161c88`, and `8bb3c6c6`.
- API-visible Copilot PR reviews posted three `Changes recommended` reviews:
  `5136420741`, `5136487314`, and `5136582836`.
- Each posted cloud review reported reviewing only 26 of 41 changed files.
- The second and third posted cloud reviews included suppressed
  `Previously missed` findings in unchanged code.
- At least 10 inline comments and 5 suppressed findings were handled after PR
  publication.
- The initial local review count before PR creation was only one formal local
  code-review agent pass, despite later language implying multiple pre-PR
  reviews.
- Maintainer time, hosted checks, review attention, and runner capacity were
  consumed by serial repair instead of one converged branch-local grooming pass.

## Structural Review-Service Defect

The posted review sequence showed the same convergence warning as #2468:

```text
Review 1: 26/41 files reviewed
Review 2: 26/41 files reviewed, Previously missed
Review 3: 26/41 files reviewed, Previously missed
```

A review service that repeatedly covers only part of the PR and later reports
unchanged-code findings must not be treated as proving convergence. It is a
signal to stop, not a reason to request another pass.

## What Went Wrong

1. The initial local review was treated as stronger evidence than it was. It
   found one real iPad issue, but it did not validate every advertised helper
   invocation, every supported platform path, or the asynchronous render-state
   contract.
2. The PR was opened after one formal local review-agent pass, while later
   reporting language implied multiple pre-PR reviews had been completed.
3. The branch relied on simulator/device success as a proxy for command-contract
   coverage. Successful `simulator --run-tests` did not prove option-first
   `--run-tests` default-target behavior.
4. The first stale-share repair did not state the correct invariant. The needed
   invariant was "a control change immediately invalidates any in-flight
   render," not merely "a later run has a newer serial."
5. Suppressed review-body findings were not treated early enough as first-class
   blockers equal to unresolved inline comments.
6. The second-cycle stop rule was not used as a hard blocker quickly enough.
   After review `5136487314`, further automated-review activity should have
   stopped until explicit maintainer direction and a complete branch-local
   audit.
7. Cloud review was allowed to become an implementation-discovery loop, which
   repeated the #2468 anti-pattern this PR was supposed to avoid.
8. The user had to point out the absurdity of repeated review misses before
   the incident was recorded for publishable governance consumption.

## Required Remediation

1. Before opening any upstream PR, record the exact formal local review count.
   Do not describe implementation grooming, test runs, or ad hoc inspection as
   multiple formal reviews.
2. For every helper script, execute all documented invocation shapes:
   positional target, default target, option-first default target, help, invalid
   target, and invalid option.
3. For every asynchronous UI workflow, write the state-machine invariant before
   review. For #2471, that invariant should have been: a user control change
   immediately invalidates all in-flight renders and disables stale export
   until the newest serial is accepted.
4. Treat any `Previously missed` review-body finding as evidence that the local
   scope model was incomplete. Stop comment-by-comment repair and rebuild the
   full `base...HEAD` contract matrix.
5. After the second automated review with a new blocker, do not patch, push,
   resolve threads, request another review, or claim readiness until the
   maintainer explicitly chooses the next action.
6. Keep a PR-local review ledger before every push after review feedback. It
   must include reviewed commit, current commit, active findings, suppressed
   findings, changed files, contracts affected, exact validation, and
   `review-stop` status.
7. Do not use unresolved-thread count as the sole closure signal. Review bodies
   and suppressed findings must have explicit dispositions.

## Required Agent Behavior Changes

1. When the user references a prior governance failure, the next action must be
   a gate and evidence ledger, not an optimistic repair or another review.
2. If asked "how many reviews," answer with separate counts for formal local
   review agents, manual grooming passes, API-visible cloud PR reviews, and any
   user-reported cloud-agent review experience. Do not collapse these into a
   favorable number.
3. If a cloud review reports partial coverage, do not cite it as a whole-PR
   readiness signal. Pair it with a local whole-surface review before any
   further publication action.
4. If a repair changes a state machine, perform a transition audit covering the
   period before, during, and after the new state change. A single pass/fail
   smoke is not enough evidence.
5. If a repair changes command parsing, test the documented commands exactly as
   written in the README and usage output, not only the internally preferred
   invocation.
6. Commit and PR comments must remain attribution-clean when the user has
   requested no Copilot attribution.

## Decision

This PR exceeded the automated-review stop threshold. The correct state after
review `5136487314` was:

```text
review-stop: FAIL - maintainer direction required
reason: a second automated review found new blockers and suppressed previously
missed findings after local readiness had been claimed
```

Review `5136582836` confirmed that the process still had not converged. The
branch-local repair at `8bb3c6c6` addressed the known technical findings, but
the process finding remains: local pre-PR review was incomplete, cloud review
was overused as discovery, and future PRs must block publication until the
complete local review ledger and contract matrix are recorded.
