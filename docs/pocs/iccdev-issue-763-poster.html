iccDEV Issue 763 / AddXform Ownership Bug

One cenc header, one stale delete

This poster is built around the exact 728-byte PoC from iccDEV issue #763. The left side is a full XXD-style dump of the profile. The right side shows why the bytes do not directly corrupt memory by themselves: they push CIccNamedColorCmm::AddXform() into the color-encoding ownership path, then the old cleanup path frees the same profile again on failure. CFL-078 keeps the rejection, but removes the double-cleanup.

Trigger Bytes 0x0C-0x0F = cenc selects the color-encoding AddXform path.
Invalid PCS 0x14-0x17 = NULL keeps the same profile on the rejection path.
Size Mismatch declared 0x02D0, actual 0x02D8, with 8 trailing bytes past the header size.
Observed Outcome pre: stale delete and HUAF. post: Invalid Profile.

Why These Bytes Matter

  • cenc is the branch selector. The cleanup bug matters only after this device class enters the special inner ownership path.
  • NULL PCS, the size mismatch, and malformed cept content keep the same profile on a failure path after ownership has already moved.
  • CFL-078 does not make the file valid. It preserves the rejection and only removes the stale caller-side delete.

Critical Header Bytes

The most important field is at 0x0C: 63 65 6E 63 = cenc. That class is what selects the color-encoding ownership path that CFL-078 guards.

Not A Normal ICC

The same header also advertises PCS='NULL', declares 720 bytes while the file is 728 bytes, and carries non-zero reserved header data. The file is supposed to fail validation.

Why The Tail Matters

cept consumes most of the file and the last 8 bytes sit past the declared size. Those bytes help drive the invalid-profile return, which is exactly where the old cleanup path touched stale ownership.

Patch Compare

The profile chooses the branch. The bug lives in cleanup. Before CFL-078, failure after the inner cenc path could reach a stale delete or detach on a profile that had already been consumed internally.

Crash Path

1. Open profile

The tool opens the PoC and sees deviceClass = cenc before any transform is built.

2. Enter inner AddXform

The cenc path is special: per CFL-078 comments, the inner creation path can delete or replace the original profile object.

3. Validation fails

The same profile also carries NULL PCS, size mismatch, private tags, and malformed cept content, so AddXform does not succeed.

4. Old cleanup was wrong

Pre-patch code still ran delete pProfile on the caller side, even though the cenc path had already taken ownership. That is the HUAF at IccCmm.cpp:10564.

CFL-078 Diff Focus

+ icProfileClassSignature savedClass = pProfile->m_Header.deviceClass;
 
 icStatusCMM rv = AddXform(pProfile, nIntent, nInterp, pPcc, nLutType,
                           bUseD2BxB2DxTags, pHintManager);
 
 if (rv != icCmmStatOk)
 if (rv != icCmmStatOk && savedClass != icSigColorEncodingClass)
   delete pProfile;

The same pattern was applied to four overloads in IccProfLib/IccCmm.cpp, including the named-color path that crashes in the issue report. The reference overload also guards CopyAttach(nullptr) so detached IO state is not touched after cenc ownership transfer.

Why This Works Better Than #700

Issue #700 is a config bug chain. Issue #763 is a compact profile-led trigger: the key branch selector is visible in the first 32 bytes, the entire file fits on one poster, and the post-patch outcome is easy to explain: the same file now exits as Invalid Profile instead of dying in cleanup at IccCmm.cpp:10564.

Analyzer Cross-Checks

  • H1: header size 720 does not match the 728-byte file.
  • H6 and CF-014: PCS is NULL instead of XYZ or Lab .
  • H40 and CF-015: reserved header bytes are non-zero.
  • H134: the cept tag carries non-zero reserved bytes.
  • CF-092 and CF-097: all three tags are private and undocumented.
